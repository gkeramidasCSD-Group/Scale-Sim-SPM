# Paper material: SCALE-Sim performance optimizations

Everything in this folder is regenerated by `python3 make_paper_assets.py`. The script reads the
four `.pstats` profiles in `../profiles/` and the un-profiled sweep in `results.csv`.
`numbers.txt` lists every number quoted below, so you can check any sentence against the data.

| File | Use |
|---|---|
| `fig_time_breakdown.pdf` | Figure: where the time goes, before and after (single column, 3.5 in) |
| `fig_speedup.pdf` | Figure: end-to-end speedup across models and configurations (single column) |
| `tables.tex` | `tab:optimizations` (full width), `tab:breakdown`, `tab:speedup` (full width), `tab:walltime`. Needs `booktabs` and `tabularx` |
| `numbers.txt` | All quoted numbers, for checking |

The PDFs embed their fonts (Type 42) and use a Times-style serif at 7–8 pt to match IEEE/ACM
body text. Colors come from a colorblind-validated palette and every segment also has a hatch,
so the breakdown figure still reads in grayscale print.

## Draft text: methodology

> **Optimizing the simulator.** Cycle-accurate simulation in SCALE-Sim is dominated by a
> Python loop that services every SRAM request of every simulated cycle. To find where that
> time goes, we profiled the unmodified simulator with Python's built-in deterministic profiler
> (cProfile). Raw per-function times scatter library work (NumPy, dictionary and set
> operations) across hundreds of entries, so we charge each library call to the simulator
> function that issued it and group functions into six components
> (Table~\ref{tab:breakdown}).
>
> Table~\ref{tab:optimizations} lists the seven changes that followed. None of them changes
> the simulation model. They remove three kinds of overhead:
> - per-cycle interpreter work that serves no purpose, such as constructing a disabled
>   progress-bar object on every cycle;
> - linear scans in the per-address hit/miss test, replaced by $O(1)$ index lookups;
> - quadratic trace construction, where every DRAM prefetch or write-buffer drain copied the
>   entire trace built so far.
>
> **Correctness.** For both profiled workloads, every output of the optimized simulator is
> byte-identical to the unmodified one: the compute, bandwidth, and detailed-access reports,
> plus all per-layer SRAM and DRAM trace files (348 files per run, compared by MD5). In the
> end-to-end sweep, total and prefetch-inclusive simulated cycle counts match in all 50
> configurations where both versions finished.
>
> **Setup.** End-to-end times are wall-clock times without profiling, averaged over three
> runs on a dedicated server (Python 3.8, NumPy 1.24). The maximum coefficient of variation
> is 3.6\% and the median is 1.0\%. Runs exceeding 90 minutes were stopped; for those we
> report the speedup as a lower bound, the time limit divided by the optimized runtime.
> The workloads are:
> - three CNNs: AlexNet (5 layers), GoogLeNet (58), and MobileNet (27);
> - two GEMM workloads: a 5-layer ViT-B slice and a 54-layer transformer.
>
> We vary the array size (16$\times$16, 64$\times$64) and the SRAM size (16\,KB, 256\,KB) in
> both of SCALE-Sim's interface-bandwidth modes. We also include SCALE-Sim's default
> configuration (32$\times$32, 64\,KB, CALC) and, for two CNNs, the output- and
> input-stationary dataflows.

*(If the profiling setup belongs in the paper:)*

> To keep memory bounded when profiling full networks, the profiling driver writes each layer's
> traces as usual and then releases that layer's simulation state. It does this identically
> for both versions, with the profiler paused during the release and the trace hashing.

## Draft text: results

> **Where the time went.** Fig.~\ref{fig:breakdown} and Table~\ref{tab:breakdown} show the
> profile before and after optimization. In CALC mode, the unmodified simulator spends
> 31.7\% of its time in hit/miss checks and 20.9\% constructing DRAM traces. Another 15.3\%
> goes to creating progress-bar objects that are never displayed, one per simulated cycle.
> In USER mode with a 32\,KB SRAM, DRAM trace construction alone takes 68.6\%: each of the
> 23\,k prefetches copies the entire read trace built so far.
>
> Deferring that concatenation (optimization~5) removes 83\% of the time saved in USER mode.
> In CALC mode, removing the progress bars (41\%) and making the hit/miss lookup constant-time
> (30\%) contribute most (Table~\ref{tab:optimizations}).
>
> After optimization, writing the trace files is the largest remaining single component:
> 20.3\% in CALC and 42.2\% in USER mode. Its absolute time is unchanged, so its share grows
> as everything else shrinks.
>
> **End-to-end speedup.** Without profiling, the optimized simulator is faster in every
> configuration (Fig.~\ref{fig:speedup}, Table~\ref{tab:speedup}):
> - across the 36 workload/configuration pairs where both versions finished, the geometric
>   mean speedup is 1.97$\times$, ranging from 1.49$\times$ to 17.0$\times$;
> - in CALC mode, the geometric mean is 1.81$\times$ (1.51--3.14$\times$). In SCALE-Sim's
>   default configuration it is 1.70$\times$ (Table~\ref{tab:walltime});
> - in USER mode, gains grow sharply as SRAM shrinks, because the removed $O(n^2)$ trace
>   copying scales with the number of prefetches. With 16\,KB SRAMs, the unmodified simulator
>   did not finish within 90 minutes in 8 configurations that the optimized version completed,
>   giving speedups of at least 4.6--17.1$\times$. One configuration completed in both versions
>   at 17.0$\times$ (MobileNet, 64$\times$64, 16\,KB: 4208\,s vs.\ 248\,s).

## What to be careful about when writing

1. **Cite speedups from the un-profiled sweep, not from the profiles.** cProfile adds a
   fixed cost per Python call, and the vanilla version makes more calls. That's why the
   profiled USER speedup (4.22×) is not an end-to-end number. Use the profiles only for the
   *breakdown* (percentages). The text above follows this rule.
2. **The two profiles ran on different machines.**
   - CALC: this laptop (Python 3.10, NumPy 1.26), versions run one after the other.
   - USER: the server (Python 3.8, NumPy 1.24), both versions in parallel.

   Percentages within one workload are comparable; don't compare absolute seconds across the
   two. For a uniform setup, rerun the CALC profile on the server, without `PARALLEL=1`:
   ```bash
   VANILLA_REPO=/data/grizos/SCALE-Sim VANILLA_PYTHON=/data/grizos/SCALE-Sim/venv/bin/python \
   OPTIMIZED_PYTHON=/data/grizos/Scale-Sim-SPM/venv/bin/python \
   TOPO=topologies/conv_nets/Googlenet.csv ARRAY=16 SRAM_KB=16 BW=CALC \
   nohup benchmark/cprofile_compare/run_network.sh > cprofile_googlenet_a16_s16_calc.log 2>&1 &
   ```
   Then copy `profiles/googlenet_a16_s16_calc_*` back and rerun `make_paper_assets.py`.
3. **Byte-identical outputs were checked in the profiled runs.** The sweep compared
   *cycle counts* only. The text says exactly this; keep the distinction.
4. **"ViT-B" is a 5-layer GEMM slice**, not the full model. Table `tab:speedup` states it.
5. **How savings are attributed to optimizations.** A function's saved time is credited to
   the optimization that changed it. The time saved in the read/write servicing loops is
   credited to optimization 1, because removing the progress bar was the only change to those
   loops. The remainder in unmodified code is listed as run-to-run variation: 6.1% of the
   CALC saving and 0.2% of the USER saving.
6. **Costs of the optimizations:**
   - peak memory: +7% in the USER run (2408 → 2588 MB) and +3% in the CALC run (2804 → 2900 MB);
   - building the USER-mode reverse index adds a small per-layer setup cost. It's already
     netted into row 4a.

   Mention these if a reviewer might ask.
7. **The sweep's optimized version** is the server checkout (`/data/grizos/Scale-Sim-SPM`)
   at the time of the sweep. If that code changed afterward, rerun the sweep for the camera-ready
   version.
